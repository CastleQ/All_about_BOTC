# 시계피 홈브류 설계 + 스크립트 JSON 제작

두 가지 일을 한다. 요청에 맞는 쪽을 고르고, 둘 다 필요하면 설계 → JSON 순서로 한다.

| 요청 | 할 일 | 참고 자료 |
|---|---|---|
| 새 캐릭터 아이디어, 능력 밸런스, 능력 문구 다듬기, 이름 짓기, 테스트 계획 | **A. 캐릭터 설계 조언** | `references/홈브류_캐릭터_설계_안내서.md` |
| 캐릭터 목록 → 스크립트 JSON, 밤 순서·징크스 정리 | **B. 스크립트 JSON 제작** | `references/json-system-prompt.yaml` |

## 공통 원칙

- 같은 플러그인의 `botc-rules-advisor` 스킬 `references/운영방침.md`의 0장 불변 규칙과 1장 용어·출처 표기를 따른다. 위치: 이 스킬 폴더의 형제 폴더 `../botc-rules-advisor/references/`, 없으면 `find / -type f -path '*botc-rules-advisor/references/운영방침.md' 2>/dev/null | head -1`로 찾는다.
- 공식 캐릭터와 비교하거나 공식 능력을 인용할 때는 그 스킬의 `references/wiki/INDEX.md`와 캐릭터 파일로 정확한 문구를 확인한다. 공식 한글 용어는 `references/Glossary_filled.csv`를 따른다.
- 홈브류 캐릭터는 반드시 "홈브류"임을 밝히고, 공식 캐릭터처럼 서술하지 않는다.
- 능력 문구에 쓴 수식어는 운영방침 1-4 "명시하지 않음 = 명시함" 원칙대로 읽힌다. 예를 들어 "이웃"과 "살아있는 이웃"은 다른 뜻이니, 의도한 쪽을 정확히 쓴다.

## A. 캐릭터 설계 조언

`references/홈브류_캐릭터_설계_안내서.md`를 읽고 그 순서대로 점검한다.

1. **위상** — 유형과 스크립트 안의 역할(정보·보호·죽음 생성 등)을 하나로 정했는가. 한 문장으로 설명되지 않으면 설계를 다시 본다(1장).
2. **플레이어 경험** — 매력 요소 6축(위력·영향력·자유도·정보력·상호작용성·독창성) 중 무엇을 노리는가. "깍두기 캐릭터"가 되지 않는가(2장).
3. **밸런스** — 비슷한 공식 캐릭터를 "표준 모델"로 삼고, 강화·약화 요소를 비교한다(3장 변형 단계).
4. **능력 문구** — "시점 → 행동 → 효과" 순서, 용어 통일, 대상 범위 명시. 4.4 체크리스트로 점검한다(4장).
5. **낮 상호작용·서사·이름** — 5~7장 기준으로 제안한다.
6. **테스트** — 9장 절차대로 테스트 계획과 피드백 질문을 제안한다.

문구 초안은 여러 버전을 나란히 보여 주고, 버전마다 해석이 갈릴 수 있는 지점과 이야기꾼 진행 부담을 함께 적는다.

## B. 스크립트 JSON 제작

`references/json-system-prompt.yaml`을 읽고 그 규칙을 그대로 따른다. 이 파일은 사람이 읽는 지침서이며 YAML 문법 검사를 통과하지 않는 줄이 있으니 파싱하지 말고 읽는다.

- 캐릭터를 뽑아 올 **마스터 JSON은 사용자가 지정한 파일만** 쓴다. 지정이 없으면 먼저 물어본다.
- 하수인 정보(`minioninfo`, 19)·악마 정보(`demoninfo`, 23)는 `_meta.firstNight` 배열에만 id로 넣고, 캐릭터 객체로 만들지 않는다.
- 검증 규칙 P1~P9를 적용하고, 자동 수정 금지 항목(P6, P9 등)은 코드를 만들기 전에 보고하고 사용자의 결정을 기다린다.
- 결과는 JSON 코드 블록을 먼저 보여 주고, 파일로도 전달한다. 저장 안내 문구는 YAML의 `output.footer`를 따른다.
