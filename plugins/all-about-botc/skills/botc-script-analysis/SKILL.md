# BOTC 커스텀 스크립트 분석 + 캡처형 이미지 제작

사용자가 시계탑에 흐른 피(BOTC) 커스텀 시트를 주며 "분석해줘", "밸런스 봐줘", "같은 방식으로 분석" 등을 요청할 때 쓴다. 이미지까지 요청하면(또는 이전에 이미지를 받았던 흐름이면) 2부 이미지 제작까지 진행한다.

## 자료 위치 (이 플러그인)

이 스킬은 같은 플러그인의 `botc-rules-advisor` 스킬 폴더에 있는 자료를 함께 쓴다. 아래에서 `<자료>`는 그 스킬의 `references/` 폴더다.

- 기본 위치: 이 스킬 폴더의 형제 폴더 `../botc-rules-advisor/references/`
- 거기에 없으면 찾는다: `find / -type f -path '*botc-rules-advisor/references/wiki/INDEX.md' 2>/dev/null | head -1`
- 파일 도구를 쓸 수 없는 환경이면 번역 위키 사이트(`https://castleq.github.io/botc-wiki-ko/c/<id>.html`)를 웹에서 연다.

## 공통 원칙 (운영방침 준수)

- `<자료>/운영방침.md`의 0장 불변 규칙과 1장 용어·출처 표기를 그대로 따른다.
- 모든 출력은 한글. 두괄식(결론 먼저). 답변 끝에 `---`로 구분하고, 사용자의 가정을 짚는 역질문 + 후속 작업 제안을 붙인다.
- 공식 캐릭터명·용어는 `Glossary_filled.csv` 한글 공식용어로만 쓴다. 상태 용어는 취함·중독·**집착**(광기 X).
- 비공식/홈브류 캐릭터·하우스룰은 반드시 출처를 밝히거나 홈브류임을 표기한다. 시트 작성자("지은이")가 보이면 "OO 님이 만든 커스텀 스크립트", 없으면 "작성자 표기가 없는 커스텀 스크립트"라고 밝힌다.
- 밸런스 권장은 `기타예외규칙.md` 0번 원칙(이야기꾼 선택 범위 안에서 선악 유리함을 가급적 맞춘다)에 근거해 쓴다.
- 밸런스 평가는 "실전 데이터가 아니라 이론상 추정"임을 표 제목에 명시한다.

## 분석 기준

1. **설계 가이드는 참고 관점일 뿐이다.** 커스텀 시트 작성·분석의 권장 기준은 Not Quite Tangible「Beginner's guide to Blood on the Clocktower custom scripts」(https://notquitetangible.blogspot.com/2024/07/clocktower-custom-scripts.html, 10개 항목)로 둔다. 다만 초보 제작자용 가이드이지 원칙·진리가 아니므로 판정 근거로 쓰지 않는다. "원칙 N"처럼 법칙인 양 인용하지 않는다.
2. **좋은 플레이 경험·재미는 전 세계 게이머의 일반론으로 판단한다.** BOTC와 소셜 디덕션을 즐기는 사람들이 보편적으로 좋아하고 싫어하는 것을 기준으로 삼는다.
3. **특정 셋업을 권하지 않는다.** 좋은 스크립트는 특정 셋업을 강요할 필요가 없다. 셋업이 적당히 무작위여도 같은 게임 경험이 유지된다(점철되는 혼란, 화단에 꽃피운 이단, 로마의 몰락, 심리사회가 좋은 사례). 특정 셋업이 필수로 따라오는 구조라면 오히려 스크립트의 피드백 포인트로 지적한다. 꼭 필요하면 "홈브류 규칙으로 명시"를 제안한다.
4. **난도 별점** — 플레이어 난도와 이야기꾼 난도를 각각 별점(★ 5점 만점)과 근거로 표기한다.
5. **출처는 공개 자료로 달고, 캐릭터 이름에는 한글 위키 링크를 건다.** 분석은 외부에 공유될 수 있으므로, 출처·근거를 사용자만 볼 수 있는 자료(로컬 파일·플러그인 내부 파일명)로 적지 않는다.
   - 분석 답변과 PDF에 나오는 **모든 캐릭터 이름**에 한글 번역 위키 링크를 건다: `https://castleq.github.io/botc-wiki-ko/c/<id>.html` (`<id>`는 위키 `INDEX.md`의 영문 id. 예: 노 다시 → `nodashii`). 답변에서는 `[노 다시](https://castleq.github.io/botc-wiki-ko/c/nodashii.html)`처럼 쓴다.
     - 같은 이름이 여러 번 나와도 매번 건다.
     - 시트 밖 캐릭터(교체 제안의 대체 후보 등)도 건다.
   - **영문 캐릭터 이름과 영문 위키 링크는 쓰지 않는다.** 출처 표기는 한글 위키 링크, 룰북, 공개된 TPI 답변 링크로 한다.
   - PDF는 HTML에서 이름을 `<a>`로 감싼다(2부 "PDF로 원할 때"의 `link_names.py`). PNG 캡처형은 링크가 눌리지 않으므로 이름 표기만 같게 두고 `<a>`는 넣지 않는다.
6. **밀주업자(Bootlegger)는 언급하지 않는다.** 사용자가 따로 요청할 때만 다룬다. 공식 스크립트 도구에 외부 JSON을 한 번이라도 넣어 내보내면 자동으로 붙는 로고이고, 한글 번역 때문에 JSON을 직접 번역해 이미지로만 출력하는 경우가 많아서다.
7. **매 분석은 독립시행이다.** 같은 대화에서 이전에 분석한 다른 시트가 있더라도 비교·대조·언급을 넣지 않는다. 각 분석은 그 시트 하나만 다루는 독립된 자료다.
8. **모자 장수는 단점으로 보지 않는다.** 판을 통째로 새로 짜는 것이 모자 장수의 존재 의의이며, 선한 팀에 처형할지 유보할지의 딜레마를 준다.
9. **4장 "나쁜 플레이 경험" 요인마다 강도(상·중·하·변동)를 매긴다.** 행은 상 → 중 → 변동 → 하 순서로 정렬한다. 강도를 판단한 근거(얼마나 자주, 누구에게, 얼마나 크게)가 "문제" 칸에 드러나게 쓴다.
   - **상:** 인원대·모임과 관계없이 자주 나타나고, 게임의 승패나 재미를 크게 해친다. 이야기꾼 운영만으로는 충분히 완화하기 어렵다.
   - **중:** 인원대·모임과 관계없이 특정 셋업(특정 악마·하수인 조합 등)에서 분명히 체감된다. 또는 이야기꾼 운영으로 일부만 완화된다.
   - **하:** 드물게 나타나거나 체감이 작다. 표의 "완화 방안"(안내·이야기꾼 운영)만으로 충분히 해결된다.
   - **변동:** 인원대(플레이어 수)나 모임의 숙련도(초보 위주/숙련자 위주)에 따라 강도가 크게 달라진다. 문제 칸에 어떤 조건에서 강해지고 약해지는지 적는다. (예: "10~11인·초보 모임에서는 상, 14~15인·숙련자 모임에서는 하")
10. **5장 "캐릭터 교체 제안" 작성 규칙**
    - **대상:** 4장에서 강도 상·중인 요인만 다룬다. 강도 하·변동인 요인에는 캐릭터 대안을 제시하지 않는다(하는 4장의 완화 방안으로 충분하고, 변동은 인원대·모임에 따라 이야기꾼이 조정할 문제이므로). 4장에 상·중 요인이 없으면 5장에는 "교체가 필요한 단점이 없다"고 쓰고 이유를 한 줄로 적는다.
    - **개수:** 제안은 1~3개만 한다. 강도 상 요인을 먼저 다룬다. 4장의 단점과 직접 연결되는 것만 쓰고, 연결 없는 취향성 교체는 쓰지 않는다.
    - **우선순위:** ① 같은 유형 교체(주민은 주민으로, 하수인은 하수인으로)를 먼저 검토한다. ② 유형 변경 교체(예: 주민 칸을 외지인으로)는 후순위다. 같은 유형 교체로 그 단점이 해결되지 않거나, 유형을 바꾸는 쪽이 분명히 더 나을 때만 제안하고, 같은 유형 교체로 부족한 이유를 근거에 적는다.
    - **유형별 개수 권장 상한:** 주민 14, 외지인 4, 하수인 4, 악마 4 이하.
      - 교체한 뒤의 시트가 권장 상한을 넘게 되는 제안은, 강도 상 요인을 해소하는 대안일 때만 제시한다. 이때 근거에 "권장 상한 초과"와 그래도 제안하는 이유를 적는다.
      - 원래 시트가 이미 권장 상한을 넘어 있다면, 같은 조건(강도 상 해소)일 때만 더 넘게 하는 교체를 제시한다. 권장 상한 쪽으로 되돌리는 교체는 언제든 제안할 수 있다.
    - **유형 변경 교체의 영향**을 근거에 함께 적는다.
      - 시트의 유형별 개수가 어떻게 바뀌는지 (예: 주민 14→13, 외지인 4→5)
      - 인원별 셋업 구성표(주민/외지인/하수인/악마 수)는 바뀌지 않는다. 대신 각 유형에서 뽑힐 후보 풀과 악의 블러핑 공간이 어떻게 달라지는지
      - 외지인 수를 바꾸는 캐릭터(대부·남작 등 [외지인 ±] 표기 캐릭터)가 있는 시트라면 그 효과가 어떻게 달라지는지
    - **대체 후보는 공식 캐릭터에서 고른다.** 캐릭터명은 `Glossary_filled.csv`의 한글 공식용어를 쓴다. 홈브류를 제안해야 할 때는 홈브류임을 반드시 표기한다.
    - **대체 후보도 번역 위키로 능력과 징크스를 확인한다.** 시트의 다른 캐릭터와 새로 생기는 징크스가 있으면 표의 마지막 칸에 위키 원문대로 적는다.
    - **시트의 콘셉트(제목·테마)를 해치는 교체는 제안하지 않는다.** 콘셉트를 지키는 범위에서 더 나은 교체가 없으면 "그대로 두는 것을 권한다"고 쓰고 이유를 적는다.
    - **기존 분석 기준을 그대로 지킨다:** 특정 셋업을 권하지 않는다(3번), 모자 장수는 단점으로 보지 않는다(8번), 밀주업자는 언급하지 않는다(6번), 다른 시트와 비교하지 않는다(7번), 출처는 공개 자료로 단다(5번).
    - **밸런스 이동:** 교체로 밸런스가 어느 쪽(선/악)으로 움직이는지 한 줄로 적는다. 2장의 밸런스 표와 모순되면 2장 내용과 함께 설명한다.
11. **자물쇠는 오염 원인이나 게임 경험 요소로 세지 않는다.** 능력을 다시 쓰거나 되돌리지 못하게 막으려고 붙은 상태·처리를 "자물쇠"라고 부른다. 게임에 영향을 주려는 장치가 아니라 캐릭터 고유의 특성이다. 그래서 "정보 오염 원인 N개" 집계, 나쁜 플레이 경험, 이야기꾼 부담 어디에도 넣지 않는다.
    - 뱀 조련사: 맞바꾼 뒤 선해진 이전 악마의 영구 중독 → 이전 악마가 다시 맞바꾸지 못하게 하는 자물쇠
    - 메제펠레스: 취하거나 중독되어 실패해도 "능력을 쓴 것"으로 처리 → 다시 시도하지 못하게 하는 자물쇠
    - 기계공: 이미 참여 중인 캐릭터를 만들려 하면 아무 변화 없이 능력이 소모됨 → 다시 시도하지 못하게 하는 자물쇠
    - **자물쇠로 보지 않는 것:** 상태가 실제 정보에 영향을 주면 오염 원인으로 센다.
      - 식인종: 악한 플레이어가 처형되면 중독. 이야기꾼이 가짜 능력 정보를 줄 수 있다.
      - 철학자: 이미 참여 중인 캐릭터를 고르면 원래 주인이 취함. 원래 주인이 받는 정보가 틀어진다.
    - 단, 자물쇠 상태도 규칙상으로는 진짜 취함·중독이다. 다른 캐릭터의 판정(예: 기예꾼)에 영향을 주는 경우는 7장 "판정할 때 미리 알아둘 점"에만 적는다.
12. **이야기꾼 부담은 "계속 신경 써야 하는 판단"만 센다.**
    - 리마인더 토큰을 한 번 올려 두면 이후 따로 신경 쓸 것이 없는 처리는 이야기꾼 부담(난도 근거, 3단계 "이야기꾼 부담")으로 세지 않는다. 예: 노 다시 이웃 중독, 이발사·뱀 조련사의 캐릭터 교체 처리.
    - 이야기꾼이 게임 결과에 큰 영향을 주는 선택을 해야 하는 경우는 부담으로 센다. 예: 꼭두각시를 악마의 양옆 중 누구로 할지. 이것은 "자리 배치"라고 쓰지 말고 "악마의 양옆 중 누구를 꼭두각시로 할지(이야기꾼 재량)"라고 쓴다.

# 1부. 분석 방법론

## 1단계: 캐릭터 목록 확정

시트에서 주민·외지인·하수인·악마·전설(설화)과 징크스 아이콘(캐릭터 이름 옆 작은 아이콘)을 모두 읽어 목록화한다. 유형별 개수도 센다.

## 2단계: 번역 위키로 검증 (필수)

위치: `<자료>/wiki/`. `ALL.md`는 이 플러그인에 없으며, 있더라도 읽지 않는다.

**자료 연결 확인 (분석 시작 전 필수):** 위키 파일도, 번역 위키 사이트도 열 수 없으면 분석을 시작하지 말고 먼저 사용자에게 이렇게 되묻는다.

> 자료가 연결되지 않아 분석이 정확하지 않을 수 있습니다. 그래도 만들까요?

- 사용자가 진행을 원하면 그때 분석을 진행한다.
- 둘 중 하나라도 열리면 묻지 않고 바로 진행한다.

1. `INDEX.md`에서 시트의 한글명으로 grep → id·유형·에디션·파일 경로 확보. 이 단계에서 **공식 캐릭터 여부**와 **실험 캐릭터 수**를 확정한다.
2. 시트 캐릭터 파일을 연다.
3. 징크스 추출 — 각 파일의 `## 징크스` 섹션에서 **양쪽 다 시트에 있는** 조합만 남긴다:

```bash
cd "<자료>/wiki/characters"
S="캐릭터1|캐릭터2|..."   # 시트의 한글 캐릭터명 전부
for f in */*.md; do o=$(awk '/^## 징크스/{p=1;next} /^## /{p=0} p' "$f" | grep -E "^- ($S) \+ ($S):"); [ -n "$o" ] && echo "=== $f" && echo "$o"; done
```

   시트의 징크스 아이콘과 위키 결과가 일치하는지 대조해 보고에 적는다.
4. 판정에 핵심인 캐릭터(악마, 외지인 수 변경자, 특이 셋업 캐릭터)는 `## 요약` 불릿을 읽어 세부 규칙을 확인한다:

```bash
awk '/^## 요약/{p=1} /^## 진행/{p=0} p' <파일들> | grep -E "^- "
```

5. 기존 `기타예외규칙.md` 항목(예: 꼭두각시×은둔자, 전도사×꼭두각시)과 연결되는 조합이 있으면 함께 적는다. 자료 간 충돌이 보이면 양쪽 출처를 모두 적고 사용자에게 알린다.

## 3단계: 분석 축

### 기본 인원 구성표 (주민/외지인/하수인/악마)
10인 7/0/2/1 · 11인 7/1/2/1 · 12인 7/2/2/1 · 13인 9/0/3/1 · 14인 9/1/3/1 · 15인 9/2/3/1

### 반드시 따져볼 것
- **정보 vs 오정보 재고 조사:** 첫날 정보 / 매일 정보 / 1회 정보 / 사망 트리거 정보로 분류. 취함·중독·오인식(위장)·집착 원인을 전부 세어 "원인 N개"로 제시. 자물쇠는 세지 않는다("분석 기준" 11번).
- **보호·생존 vs 처치 압력:** 보호 캐릭터 수, 악마 처치 빈도, 추가 처치(암살자 등), 처형 방어(악마의 변호사 등). 게임 길이를 추정.
- **외지인 성향:** 외지인은 원래 선에게 손해를 주는 역할이므로 "외지인이 늘면 누구 이득"은 결론으로 내지 않는다. 시트의 외지인 대부분이 선에게 이득이라 일반적인 경우와 반대일 때만 적는다. 외지인 수 변경자(남작, 팡 구, 카잘리, 잔 등)는 그 시트에서 구체적으로 무엇을 바꾸는지와 연결해 본다.
- **악마별 특징:** 악마끼리 무엇으로 구별되는지(처치 방식/셋업 변형/중독 패턴), 선이 악마를 판별할 단서.
- **인원 스케일링:** 소인원(하수인 2)에서 한 방 카운터(예: 전도사)의 비중, 대인원에서 정보 희석·블러핑 공간·투표력 변화.
- **이야기꾼 레버:** "~할 수도 있습니다"·임의 정보·외지인 ±?·잔의 X·기억상실자 능력 등 밸런스를 좌우하는 이야기꾼 선택지 → 구체적 권장값 제시.
- **이야기꾼 부담:** 실험 캐릭터 수, 첫날 밤 처리량, 집착 판정, 수학자류 집계, 게임 결과를 좌우하는 이야기꾼 재량. 자물쇠와 리마인더 토큰 한 번으로 끝나는 처리는 세지 않는다("분석 기준" 11·12번).

## 4단계: 보고 구조 (이 순서·형식 고정)

1. **결론 문단** — 가장 균형 좋은 인원대, 소/대인원 경향, 핵심 재미(콘셉트), 약점 3가지. 이어서 **플레이어 난도·이야기꾼 난도를 별점(★ 5점 만점)과 근거**로 적는다.
2. **인용 블록** — 작성자/출처, 공식 캐릭터 확인 여부, 실험 캐릭터 수와 목록.
3. `---`
4. `## 1. 구성 요약` — 표(유형 | 구성 | 성격) + 징크스 행 → **중요:** 핵심 구조 통찰(오정보 원인 수 등).
5. `## 2. 인원별 선악 밸런스 (실전 데이터가 아니라 이론상 추정)` — 표(악마 × 10~11인/12~13인/14~15인) → 특수 변수 문단 → **인원대별 판단 근거**(불릿) → **이야기꾼 운영 권장** (기타예외규칙 0번 원칙, 번호 목록). 외지인 ± 선택을 권할 때는 "외지인은 악에게 이득" 같은 일반론이 아니라 그 시트의 구체적 이유를 적는다(예: 대부의 추가 처치 기회, 특정 외지인의 즉시 패배 위험).
6. `## 3. 좋은 플레이 경험을 만드는 요인` — 굵은 소제목 불릿.
7. `## 4. 나쁜 플레이 경험을 만드는 요인` — 표(요인 | 강도 | 문제 | 완화 방안). 강도는 상·중·하·변동, 행은 상 → 중 → 변동 → 하 순서("분석 기준" 9번).
8. `## 5. 캐릭터 교체 제안` — 4장의 강도 상·중 단점을 캐릭터 교체로 보완하는 방법("분석 기준" 10번). 표(교체할 캐릭터 | 대체 후보 | 교체 방식(같은 유형 / 유형 변경) | 해결하는 단점(4장의 어느 행인지, 강도 포함) | 새로 생기는 문제·징크스). 같은 유형 교체를 표 위쪽에, 유형 변경 교체를 아래쪽에 둔다. 표 아래에 제안마다 1~2줄 근거(밸런스 이동 방향 포함)를 단다.
9. `## 6. 캐릭터별 존재감` — 표(높음/중간/낮음) + 불균형 지점 + "균등 분배가 꼭 정답은 아니다(조용한 캐릭터 = 블러핑 공간)" 관점과 손볼 칸 제안. 손볼 칸 제안에는 교체안을 직접 쓰지 않고 "5장 참고"로 연결한다(같은 제안을 두 번 쓰지 않는다).
10. `## 7. 판정할 때 미리 알아둘 점` — 징크스 위키 원문, 기타예외규칙 연결, 헷갈리기 쉬운 상호작용.
11. `---` + 역질문 + 후속 제안(이미지화, PDF, 문서화 등).


# 2부. 캡처형 이미지 제작

요청 시 분석 답변을 **한 글자도 빠짐없이** 그대로 옮겨 세로로 긴 PNG 한 장으로 만든다.

## 규칙
- 맨 위에 제목: `<h1>{{시트이름}} 분석</h1>` (크게, 굵게). 시트이름은 시트 상단 표기 그대로(예: `Devil's Plan 1.2`, `Who doesn't learn the numbers?`).
- 본문은 답변 원문 그대로 HTML로 옮긴다(요약·수정 금지). 표·불릿·인용·`---` 구분선 구조 유지.
- **항상 PNG + 원본 화질 zip을 함께 보낸다.** (대화창 미리보기는 세로 8000px 초과 시 축소됨)

## HTML 템플릿 (작업 폴더에 저장)

```html
<!doctype html>
<html lang="ko"><head><meta charset="utf-8">
<style>
body{margin:0;background:#f5f4ef;font-family:"Noto Sans CJK KR","Noto Sans KR",sans-serif;color:#1f1e1c;}
.wrap{box-sizing:border-box;width:1000px;margin:0 auto;padding:44px 52px 52px;background:#fbfaf6;}
h1{font-size:40px;font-weight:900;line-height:1.3;margin:0 0 28px;padding-bottom:20px;border-bottom:3px solid #1f1e1c;}
```

## 렌더링 (Playwright, 사전 설치된 Chromium 사용 — `playwright install` 금지)

Playwright나 Chromium이 없는 환경이면 이미지 대신 HTML 파일을 전달하고, 브라우저에서 열어 캡처하면 된다고 안내한다.

```bash
cd <작업 폴더> && mkdir -p out && python3 -c "
from playwright.sync_api import sync_playwright
import os
with sync_playwright() as p:
    b=p.chromium.launch(); pg=b.new_page(viewport={'width':1000,'height':800},device_scale_factor=2)
    pg.goto('file://'+os.path.abspath('cap.html')); pg.wait_for_timeout(500)
    pg.screenshot(path='out/<파일명>_분석.png',full_page=True); b.close()
"
```

- 결과 폭은 2000px이어야 한다(아니면 레이아웃 오버플로 → 수정 후 재렌더).
- 파일명: 시트이름을 영문/숫자/밑줄로 정리 + `_분석.png` (예: `Devils_Plan_1.2_분석.png`).

## PDF로 원할 때

사용자가 PDF를 원하면 같은 HTML을 PDF로 저장하되, 아래 쪽 구성과 스타일을 더한다. (PNG 캡처형은 이 규칙을 적용하지 않고 위 템플릿 그대로 만든다.)

### 쪽 구성
- **1쪽:** 제목, 결론 문단, 난도 별점, 출처 인용 블록까지.
- **2쪽:** 사용자가 준 캐릭터 시트 이미지 한 장을 한 쪽 전체에 넣는다(가운데 정렬, 비율 유지, `max-width:100%`, `max-height` 약 268mm, 얇은 테두리).
  - 이미지는 대화에 올라온 원본 파일을 작업 폴더에 복사해서 HTML의 `<img>`로 넣는다.
  - 시트 이미지가 여러 장이면 순서대로 한 장에 한 쪽씩 넣는다.
  - 시트를 JSON으로만 받아 이미지가 없으면 이 쪽은 건너뛰고, 전달할 때 "시트 이미지가 없어 2쪽을 생략했다"고 한 줄 알린다.
- **3쪽부터:** `## 1. 구성 요약`을 새 쪽에서 시작한다.

### 추가 스타일과 마크업

```html
<style>
tr{page-break-inside:avoid}
h2{page-break-after:avoid}
.newpage{page-break-before:always}
.sheet{text-align:center}
.sheet img{max-width:100%;max-height:268mm;object-fit:contain;border:1px solid #d9d6cc}
.keep{page-break-inside:avoid}   /* 짧은 표: h2와 표를 함께 묶는다 */
li{page-break-inside:avoid}
@media print{
  .wrap{width:auto;padding:0}   /* A4 너비를 넘지 않게 */
  p,li{font-size:14.5px;line-height:1.6;margin-bottom:8px}
  h1{font-size:32px} h2{font-size:20px} table{font-size:13.5px}
  blockquote p{margin:3px 0}
}
a{color:inherit;text-decoration:underline;text-decoration-color:#b9b3a3}
</style>

<!-- 1쪽: h1 · 결론 · 난도 · 인용 블록 -->
<div class="newpage sheet"><img src="sheet1.png" alt="캐릭터 시트"></div>
<!-- 시트가 여러 장이면 같은 div를 장마다 반복 -->
<div class="newpage">
  <div class="keep"><h2>1. 구성 요약</h2><table>…</table></div>
  …
</div>
```

- 쪽 나누기는 `page-break-before:always`(`.newpage`)로 한다.
- 장 제목(`h2`)이 표와 다른 쪽으로 갈라지지 않게 한다: `h2`에 `page-break-after:avoid`를 두고, 표가 짧으면(한 쪽 안에 들어가면) `h2`와 표를 `.keep`으로 묶는다. 긴 표는 묶지 않는다(빈 쪽이 생긴다).
- 인쇄용 글자 크기는 위 `@media print` 값으로 고정한다. 목록 항목은 `li{page-break-inside:avoid}`로 쪽 경계에서 잘리지 않게 한다.
- **1쪽 넘침:** 1쪽에는 제목, 결론, 난도 별점, 출처 인용 블록이 모두 들어가야 한다. 넘쳤다면 글자 크기를 더 줄이지 말고, 결론 문단과 난도 근거 문장을 줄여서 1쪽에 맞춘 뒤 다시 만든다. 분석 답변 본문에도 같은 수정을 반영한다.
- **긴 표의 머리 줄만 쪽 끝에 남으면**(예: 4장), 그 장을 `.newpage`로 새 쪽에서 시작한다.

### 캐릭터 이름 링크

HTML을 다 쓴 뒤, PDF로 만들기 전에 이 스킬 폴더의 `link_names.py`로 모든 캐릭터 이름을 한글 위키 링크로 감싼다. 긴 이름부터 바꾸고, 다른 낱말 속 이름(예: "대부분" 속 "대부")은 건드리지 않으며, 끝나면 링크 id가 모두 `INDEX.md`에 있는지 확인한다.

```bash
python3 <이 스킬 폴더>/link_names.py "<자료>/wiki/INDEX.md" cap.html cap_pdf.html
```

- PDF는 `cap_pdf.html`로 만들고, PNG는 링크 없는 `cap.html`로 만든다.
- 바꾼 뒤 결과를 훑어, 캐릭터가 아닌 일반 낱말 뜻으로 쓴 곳(예: 장터 뜻의 "시장")에 링크가 걸렸으면 그 `<a>`를 지운다. 조사 아닌 말이 붙어 링크가 빠진 이름이 있으면 손으로 감싼다.

### PDF 만들기

```bash
cd <작업 폴더> && python3 -c "
from playwright.sync_api import sync_playwright
import os
with sync_playwright() as p:
    b=p.chromium.launch(); pg=b.new_page()
    pg.goto('file://'+os.path.abspath('cap_pdf.html')); pg.wait_for_timeout(500)
    pg.pdf(path='out/<파일명>_분석.pdf',format='A4',print_background=True,margin={'top':'12mm','bottom':'12mm','left':'10mm','right':'10mm'}); b.close()
"
```

### PDF 검수

PDF를 쪽별 이미지로 바꿔 한 장에 이어 붙여 보고, ① 1쪽 끝에 출처 인용 블록이 있는지(넘쳤으면 위 "1쪽 넘침"대로 고친다), ② 2쪽이 시트 이미지로 시작하는지(이미지가 있을 때), ③ `1. 구성 요약`이 3쪽에서 시작하는지(시트 이미지가 N장이면 2+N쪽), ④ 장 제목과 표가 다른 쪽으로 갈라지지 않았는지, 긴 표의 머리 줄만 쪽 끝에 남지 않았는지 확인한다.

```bash
cd <작업 폴더> && pdftoppm -r 40 -png out/<파일명>_분석.pdf pg && python3 -c "
from PIL import Image
import glob
ims=[Image.open(f) for f in sorted(glob.glob('pg-*.png'))]
w=sum(i.width for i in ims)+10*len(ims); h=max(i.height for i in ims)
s=Image.new('RGB',(w,h),'white'); x=0
for i in ims: s.paste(i,(x,0)); x+=i.width+10
s.save('pdf_pages.png')
"
```

`pdf_pages.png`를 Read로 직접 본다. 쪽이 많아 너무 작으면 몇 쪽씩 나눠 붙인다. `pdftoppm`이 없으면 `pip install pymupdf` 후 `fitz`로 쪽별 이미지를 만든다.

## 검수

이미지를 3등분 크롭·축소해 Read로 직접 보고, 글자 깨짐·표 줄바꿈·누락이 없는지 확인한다:

```bash
python3 -c "
from PIL import Image
im=Image.open('out/<파일명>_분석.png');w,h=im.size
for i in range(3): im.crop((0,i*h//3,w,(i+1)*h//3)).resize((1000,h//6)).save(f'q{i}.png')
"
```

## 전달

1. 무압축 zip 생성: `zip -0 -q out/<묶음이름>_원본.zip out/<파일명>_분석.png ...` → `unzip -l`로 확인.
2. PNG와 zip을 **함께** 사용자에게 파일로 보낸다.
3. 답변에 원본 해상도(가로×세로 px)를 적는다. 미리보기가 축소됐다면 zip이 원본임을 한 줄로 알린다.
